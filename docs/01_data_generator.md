# Digital banking source data generator

## 1. Domain overview
- Simulates a digital banking source system.
- Generates batch and streaming-style source data.
- Used as input for the Section 02 ingestion pipeline.
- Uses synthetic data due to banking data sensitivity.
- Treated as raw source-system export data.
---

## 2. Offline dataset design

| Dataset | Grain | Primary Key | Key Relationships | Purpose |
|---|---|---|---|---|
| customers | one row per customer | customer_id | none | Customer profile and segment information |
| accounts | one row per bank account | account_id | customer_id | Bank account information |
| cards | one row per card | card_id | customer_id, account_id| Card ownership and status |
| merchants | one row per merchant | merchant_id | none | Merchant category, city, and risk level |
| historical_transactions  | one row per transaction event, plus injected duplicates | transaction_id | customer_id, account_id, card_id, merchant_id | Historical transaction records used for facts and features |
| fraud_cases | one row per fraud case | case_id | transaction_id, customer_id | Label source for confirmed or reviewed fraud cases |
---

## 3. Streaming dataset design

| Stream | Grain | Event Key | Main Timestamp | Purpose |
|---|---|---|---|---|
| transaction_events | one row per transaction event, plus injected duplicates | event_id | event_timestamp | Simulates real-time transaction authorization/decline events |
| login_events | one row per login attempt | event_id | event_timestamp | Supports login-risk and failed-login features |
| device_events | one row per device activity | event_id | event_timestamp | Supports new-device and device-change features |
| fraud_alert_events | one row per rule-based alert | event_id | event_timestamp | Simulates alerts generated by a fraud rule engine |

## 4. Key schema and grain decisions

### 4.1 Timestamp columns

| Column | Meaning |
|---|---|
| event_timestamp | Business event time when a transaction or event happened |
| created_ts | Record creation or source availability time |
| signup_ts | Customer signup time |
| open_ts | Account opening time |
| issued_ts | Card issued time |
| case_open_ts | Fraud case opening time |

| Column | Meaning |
|---|---|
| customer_id | Customer business key |
| account_id | Account business key |
| card_id | Card business key |
| merchant_id | Merchant business key |
| transaction_id | Transaction business key |
| event_id | Streaming event identifier |

### 4.3 Main transaction columns

| Column | Description |
|---|---|
| transaction_id | Unique transaction identifier before duplicate injection |
| customer_id | Customer performing the transaction |
| account_id | Account used in the transaction |
| card_id | Card used, nullable for non-card transactions |
| merchant_id | Merchant receiving the transaction |
| event_timestamp | Transaction event time |
| created_ts | Transaction record creation time |
| amount | Transaction amount in VND |

## 5. Generation configuration and logic

### 5.1 Key configuration parameters

| Area | Parameter | Value | Purpose |
|---|---|---:|---|
| Project | random_seed | 42 | Reproducible generation |
| Time range | start_date | 2025-01-01 | Start of transaction history |
| Time range | end_date | 2025-03-31 | End of transaction history |
| Entities | n_customers | 10,000 | Number of generated customers |
| Entities | n_merchants | 3,000 | Number of generated merchants |
| Behavior | avg_transactions_per_customer_per_month | 12 | Controls transaction volume |
| Behavior | base_fraud_rate | 0.003 | Base fraud probability before risk adjustments |
| Data quality | duplicate_transaction_rate | 0.02 | Inject duplicate transaction rows |
| Data quality | duplicate_event_rate | 0.015 | Inject duplicate stream events |
| Data quality | late_arrival_rate | 0.10 | Inject late-arriving records |
| Data quality | missing_device_id_rate | 0.05 | Inject missing device identifiers |
| Data quality | missing_merchant_category_rate | 0.03 | Inject missing merchant categories |
| Schema evolution | schema_change_date | 2025-02-15 | Records before this date follow an older schema |

### 5.2 Generation process

The generator follows four main steps:

1. Generate reference entities: create customers, accounts, cards, and merchants. Customer behavior depends on customer_segment, while merchant risk depends on merchant_category and risk_level.

2. Generate transactions: sample customers, accounts, cards, and merchants to create historical transactions. Transaction amount is generated using a skewed distribution so that most transactions are small and a smaller number of transactions are unusually large.

3. Assign fraud labels: calculate a fraud probability for each transaction from a base fraud rate and additional risk signals, including high-risk merchants, high transaction amount, foreign IP country, new device, and night-time activity. The final is_fraud label is sampled from this probability.

4. Generate streaming-style events: create transaction, login, device, and fraud alert events from the generated source entities and transactions. These files simulate upstream event streams from digital banking services.

The generator writes a quality report after the data is created, so the generated row counts, duplicate rates, late-arrival rates, missing-value rates, schema evolution checks, skew checks, and cardinality checks can be reviewed.

## 6. Injected data problems

| Challenge | Where It Appears | Why It Matters Downstream |
|---|---|---|
| Skewed distribution | Customer city and merchant category | Tests partitioning, aggregation, and skew-aware processing |
| High-cardinality IDs | customer, transaction, device, merchant IDs | Tests joins, deduplication, and feature grouping |
| Duplicate transaction rows | historical_transactions | Requires Silver deduplication by business key and latest created_ts |
| Duplicate stream events | transaction_events | Requires event deduplication by event_id |
| Late arrivals | transactions/events with delayed created_ts | Requires event-time handling and late-data policy |
| Out-of-order events | streaming JSONL files | Tests streaming ingestion assumptions |
| Missing values | device_id, merchant_category | Requires null handling and quality checks |
| Schema evolution | records before 2025-02-15 miss device_id, ip_country, channel | Tests schema compatibility and update policy |

## 8. Operational notes and run instructions

### 8.1 Failure handling

The generator creates required directories automatically and fails fast if the configuration is invalid. Failed runs can be safely repeated using the same configuration.

### 8.2 Observability

The generator writes execution logs to: logs/01_generate_data.log

The quality report is written to: reports/01_generation_report.md

### 8.3 Security notes

All generated data is synthetic and does not contain real banking information.

In production environments, sensitive data would require masking, encryption, and access control.

### 8.4 Run instructions

Install dependencies:

```bash
pip install -r requirements.txt
```

Run the generator:

```bash
python src/generate_data.py --config configs/generator_config.yaml
```

Expected evidence:

reports/01_generation_report.md
logs/01_generate_data.log
data/source/offline/*.parquet
data/source/stream/*.jsonl

Example execution log:

```bash
INFO | Starting data generation
INFO | Using random seed: 42
INFO | Wrote generation report to reports/01_generation_report.md
INFO | Data generation completed successfully
```
